# ADR-001 服务发现：继续禁用 Nacos，采用静态实例解析

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳（沿用 zx-learn 底座决策）；**2026-09-22 复核并补齐依据** |
| **决策** | **不引入 Nacos**（维持 `NACOS_ENABLED=false`），服务发现走 `SimpleDiscoveryClient` 静态实例 |
| **影响面** | 8 个服务（9080–9087）、网关路由表、服务间 5 个 Feign 客户端 |
| **备选方案** | ① 维持现状静态直连 ② 网关补 `loadbalancer` + `lb://` + 静态实例列表 ③ 引入 Nacos 注册中心 |
| **建议** | 采 **①**，并在需要横向扩容前做 **②** 的低成本改造；**③ 仅在本 ADR §5 触发条件出现时启用** |

> 本文所有结论均为**实测所得**（读源码 / 拆 JAR / 查运行日志），
> 凡未实测的推断已显式标注「未验证」。原始依据见附录 A。

---

## 1. 背景

CodeJudge 从 zx-learn 底座改造而来，底座默认关闭 Nacos。项目实际部署形态是
**单机房 Docker Compose**（`docker-compose.yml` 只定义基础设施：MySQL 3307 / Redis 6380 /
PostgreSQL 5433 / RocketMQ / MinIO），8 个 Spring Boot 服务以 `java -jar` 起在宿主机上。

需要回答的问题：**这套形态下，注册中心带来的是净收益还是净成本？**

---

## 2. 现状实测（2026-09-22）

### 2.1 配置事实

| 项 | 实测值 | 来源 |
|---|---|---|
| 开关 | `NACOS_ENABLED=false` / `NACOS_CONFIG_ENABLED=false` | `.env` L63–64，`.env.example` 同 |
| 注册地址 | `NACOS_ADDR=localhost:8848`（占位） | 同上 |
| 依赖 | **8 个服务全部引入了** `spring-cloud-starter-alibaba-nacos-discovery` 2023.0.3.2 + `-nacos-config` | 各模块 `pom.xml` |
| Nacos 容器 | **不存在** —— `docker-compose.yml` 与 `deploy/` 内零 Nacos 定义 | grep 实测为空 |

### 2.2 两条寻址链路（关键：它们用的是**两套不同机制**）

| 链路 | 机制 | 配置位置 | 扩容一个实例的代价 |
|---|---|---|---|
| **南北向**（网关 → 服务） | `uri: ${GW_*_URI:http://localhost:90xx}` **静态 http 直连，单值** | `judge-gateway/application.yml` 9 处 | 改配置 → **重启网关**（唯一入口，瞬断） |
| **东西向**（服务 → 服务） | `@FeignClient(value="judge-xxx")` **服务名** → `SimpleDiscoveryClient` 解析 `simple.instances` **静态列表** | 各服务 yml + `judge-api` | 改配置 → **重启该服务**（网关不动） |

> ⚠️ **东西向调用用的是服务名，不是静态 `url`**：实测 5 个 Feign 客户端
> 全部用**服务名**（`value = "judge-ai" / "judge-auth" / "judge-contest" / "judge-problem" / "judge-submission"`），
> 由 `simple.instances` 提供实例地址。这个区别不是措辞问题：
> - 静态 `url` = 地址硬编码进 Java 代码 → 换环境要改代码；
> - 服务名 + 实例列表 = **代码零改动、环境差异全在配置** → 这才是能平滑切 Nacos 的前提。

### 2.3 依赖能力差异（决定切换工作量）

拆 JAR 实测：

| 模块 | 含 `loadbalancer` | 含 `nacos-client` |
|---|---|---|
| `judge-gateway` | ❌ **无** | ✅ 8 个 nacos 件（2.4.2） |
| `judge-auth` | ✅ `spring-cloud-starter-loadbalancer-4.1.4` | ✅ 8 个 |
| `judge-user` | ✅ 同左 | ✅ 8 个 |

**结论（依赖链已实证）**：`judge-api/pom.xml` 显式引入 `spring-cloud-starter-loadbalancer`，
注释原文为「服务名负载均衡：本地直连/生产 Nacos 均依赖它解析 Feign 目标地址」——
底座作者当时已为 Nacos 场景预留；`judge-auth` / `judge-user` 均依赖 `judge-api` → 传递获得；
而 **`judge-gateway` 不依赖 `judge-api`（实测 0 处引用）**，所以网关路由**当前无法使用 `lb://`**。

### 2.4 运行时行为（关闭态的真实开销）

启动日志中 Nacos 相关行数：gateway 96 / user 72 / auth 68 / submission 68 / problem 64 /
worker 64 / contest 48 / ai 28 —— 逐条核对后**全部是 `NacosLogging` 日志适配器初始化**，
**零连接尝试、零 WARN、零 ERROR**（无 `NamingService`、无 8848 连接、无 `NacosException`）。

即：关闭态下 Nacos 是「**classpath 上躺着、不干活**」，成本仅为类加载与启动噪音，可忽略。

---

## 3. 决策

**继续禁用 Nacos。** 服务发现维持 `SimpleDiscoveryClient` 静态实例 + 网关 `GW_*_URI` 直连。

**并且明确**：`NACOS_ENABLED=true` 目前是一条**从未被验证过的休眠路径**（见 §6.2），
不应把它当作「随时可翻的开关」写进部署文档。

---

## 4. 判断依据（五个维度）

### 4.1 适用场景匹配度 —— 不匹配

注册中心的价值只有两个来源：**动态发现**（实例上下线自动感知）与**动态配置**（不停机改配置）。
它们成立的前提是「实例集合频繁变化」或「配置需在线调整」。

| 判据 | Nacos 需要 | CodeJudge 实际 |
|---|---|---|
| 实例数 / 变更频率 | 数十~上百，日常扩缩容 | 8 服务 × 1 实例，扩容是**低频人工操作** |
| 部署编排 | K8s / 多机房 | 单机房 Docker Compose |
| 配置变更频率 | 高（在线调参） | 低（改 `.env` 重启，8 服务重启 < 1 分钟） |

**最需要横向扩容的组件恰好不需要服务发现**：判题机 `judge-worker`（瓶颈 ≈ 1.5 题/s，是全系统最先饱和的一环）
靠 **MQ 消费组天然分流**，加实例即加消费者，与注册中心无关。这是本决策最有力的论据——
Nacos 能解决的痛点，在 CodeJudge 里已经有更简单的解。

### 4.2 优缺点对比

| 维度 | 静态实例（禁用） | Nacos（引入） |
|---|---|---|
| 服务上下线感知 | 手工改配置 + 重启 | 自动、秒级 |
| 网关扩容代价 | **需重启网关（入口瞬断）** | 实例自注册，网关不动 |
| 组件数量 | 0 新增 | +1（且 Nacos 自身需 MySQL 存配置，或内置 Derby 单机不持久） |
| 故障域 | 无新增 | Nacos 成为**必须健康**的关键路径；挂了则路由退化/新实例无法注册 |
| 启动顺序耦合 | 无 | 服务启动依赖注册中心可达 |
| 配置管理 | `.env` + 重启 | 配置中心在线推送（本项目未使用该能力） |
| 排障难度 | 配置即真相，链路直观 | 「服务明明起了为什么路由不到」类问题排查成本高 |

### 4.3 性能与运维成本

**性能**：关闭态实测零连接尝试（§2.4），无性能开销。引入后每实例需维持**长连接心跳**
（Nacos 客户端默认 5s 心跳；服务端 15s 未收到即标记不健康、30s 剔除），8→N 实例的心跳与推送流量虽小，
但增加了**健康检查抖动导致路由短暂丢失**这一类故障模式——在吞吐远未饱和的当前阶段，
为换取「扩容省一次重启」而引入一个新的可用性风险点，不划算。

**可量化参照**：本项目实测 Web 层 **3 108.8 req/s**（500 req/s 门槛的 6.2×），
瓶颈明确在判题机而非路由。注册中心不解决任何当前瓶颈。

**运维成本**：+1 个需监控/备份/升级/鉴权（默认 `nacos/nacos` 弱口令）的有状态组件；
需额外定义命名空间/分组规范；并且**它自己是单点**（要消除单点须 ≥3 节点 + 前置 LB）——
对一个 8 服务的单机房系统属于明显的过度设计。

### 4.4 与现有技术栈的兼容性 —— **良好，但网关有硬缺口**

| 兼容性判定 | 结论 |
|---|---|
| 依赖是否在位 | ✅ 8 个服务已引入 nacos-discovery / nacos-config（底座遗留），**无需加依赖** |
| Java 代码改动 | ✅ **零** —— Feign 已用服务名，走 `DiscoveryClient` 抽象，换实现不动代码 |
| 网关能否 `lb://` | ❌ **不能** —— 网关 JAR 内**无 `loadbalancer`**，必须补依赖才能用 `lb://` |
| 注解/框架冲突 | ✅ 与 Spring Cloud 2023.0.3 / SCA 2023.0.3.2 版本线一致 |
| 配置开关 | ✅ `spring.cloud.nacos.discovery.enabled` 是 SCA 标准开关，语义清晰 |

> 兼容性结论：**"能切"但**"不是翻个布尔值就能切"**——网关需补 `loadbalancer` 依赖，
> 且切换后 `simple.instances` 与 Nacos 客户端是否共存需要实测（见 §6.2）。

### 4.5 潜在风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **休眠开关陷阱**（中） | 文档写「生产置 `NACOS_ENABLED=true`」，但 compose 里**没有 Nacos 容器**。真按此操作又未部署 Nacos，服务会持续重试连接 8848。SCA 的 `fail-fast` 默认为 `false`，**推断**不会阻断启动但会刷错误日志并拖慢启动 —— ⚠️ **本项目未实测** | 要么补上「须先部署 Nacos ≥1 节点」的前置步骤，要么删除这句承诺 |
| **双 DiscoveryClient 共存**（中） | 启用 Nacos 后，`simple.instances` 配置的 `SimpleDiscoveryClient` 与 `NacosDiscoveryClient` 可能同时注册，被 `CompositeDiscoveryClient` 聚合，产生「以为切了、其实两套都在」的不可预期行为 | 切换时显式清空 `simple.instances`，并**实测验证**只剩一套 |
| **静默失效家族**（低） | 与本项目已知的兜底口令（`ADMIN_BOOTSTRAP_INIT_PASSWORD`）同族：配置了但没生效、且不报错 | 纳入 `scripts/preflight-check.py` 的检查面 |
| **注册中心单点**（中） | 若引入，Nacos 自身成为关键路径单点 | 引入时必须 ≥3 节点 + 前置 LB，成本进一步上升 |

## 5. 何时应推翻本决策（触发条件）

出现**任一**条件时，重新评估并启用 Nacos：

1. **单服务实例数稳定 > 5**，且扩缩容频率 ≥ 每周 —— 手工改配置成为真实负担；
2. **迁入 K8s** —— 此时优先用 K8s 原生 Service/Endpoints；若仍需 Nacos，通常是看中其**配置中心**能力；
3. **需要配置中心**（独立于服务发现的需求）—— 如需要在线调参不停机（告警阈值、限流参数）；
4. **多机房 / 多环境统一寻址** —— 环境维度的地址管理复杂度超过注册中心本身的成本。

> 注意：触发条件 3 与 1/2/4 **是两件事**。服务发现不需要 Nacos，
> 不代表配置中心也不需要 —— 届时应作为独立决策分别评估。

## 6. 后果与技术债

### 6.1 已知后果（接受）

- 新增实例须改配置并重启（网关侧还会瞬断）；
- 无在线配置推送，改配置 = 重启服务；
- 服务间调用地址以配置形式存在，**不是**自发现。

### 6.2 技术债（建议排期）

| # | 事项 | 说明 |
|---|---|---|
| D1 | **网关补 `loadbalancer` + 路由改 `lb://`** | 打通多实例通道，**零新增组件**即可去掉「扩容必须重启网关」这一最大痛点。属低成本预防性改造，建议在首次横向扩容前完成 |
| D2 | **处置 `NACOS_ENABLED` 的语义** | 二选一：① 补「须先部署 Nacos」前置步骤并**实测一次**切换；② 明确标注「未验证路径，切换前必须实测」 |
| D3 | 统一寻址心智 | 网关静态直连 vs 服务间服务名解析，两套机制并存，运维需同时理解。D1 完成后可收敛为一套（都用 `lb://` + `simple.instances`） |

### 6.3 本次复核**未验证**的事项（不编造）

1. `NACOS_ENABLED=true` + 无 Nacos 服务器时，8 个服务的**真实启动行为**（是否阻断、重试间隔）；
2. 启用 Nacos 后 `simple.instances` 是否仍生效（双 DiscoveryClient 共存问题）；
3. 网关由静态 `uri` 改 `lb://` 后的端到端时延与故障转移表现；
4. Nacos 引入后的心跳/推送开销实测值。

> 上述 4 项都需要起一套 Nacos 才能测，本轮未做。**任何一项结论都不得在未实测前写进部署手册。**
