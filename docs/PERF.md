⚠️ **三条必须理解的限制**：

1. **压测工具与业务服务同机** —— 这是**容量下界**，不是生产预期。生产压测必须在独立压测机执行。

   会把登录吞吐钳死在 2 req/s（详见 `perf-test/README.md` §3.3）。默认值本身不变。
3. **submit 场景不含判题耗时** —— `POST /submissions` 是异步入口（幂等检查 + 落库 + 入队即返回），
   判题由沙箱在 `judge-worker` 侧秒级完成，其观察口径是 `judge_queue_backlog`，不是 HTTP 延迟。

### 3.2 吞吐未达标 —— 归因分析

**结论：这不是系统容量问题，是负载模型与门槛不匹配。** 依据如下。

**依据 1（算术）**：本计划的**总工作量是固定的**（由 loop 数决定，约 5890 个请求），
运行在 loop 跑完即结束。而各线程组的 ramp-up 合计 60s，因此
**观测吞吐的算术上限 ≈ 总工作量 / ramp 时长 = 5890 / 60 ≈ 98 req/s**。
实测 102.7 req/s 已在该上限附近 —— 也就是说，**无论服务多快，这个计划都跑不出 500 req/s**。

**依据 2（实测：工作量放大探针）**。命令：

```bash
python perf-test/run-perf.py --plan load --no-html \
    -J tgBrowse.loops=150 -J tgHistory.loops=90 -J tgRank.loops=120
```

只放大**只读**场景的工作量（submit 保持 10 轮，避免把判题队列冲爆），结果：

| 指标 | 标准跑（×1 工作量） | 探针（×2.77 工作量） | 变化 |
|---|---:|---:|---|
| 总请求数 | 5890 | **16290** | ×2.77 |
| 有效窗口 | 57.4s | 57.9s | 基本不变 |
| **观测吞吐** | **102.7 req/s** | **281.4 req/s** | **×2.74** |
| 错误数 | 0 | **0** | — |
| 最差 P95（登录） | 146.0ms | 136.6ms | 未劣化 |
| `GET /problems/page` P95 | 22.0ms | 22.0ms | 不变 |
| `GET /contests/{id}/rank` P95 | 60.0ms | 77.0ms | +28% |
| `POST /submissions` P95 | 91.0ms | 110.9ms | +22% |

**吞吐随工作量近似线性上升（×2.74），而延迟几乎没有劣化、错误率仍为 0。**
这就是「计划是工作量受限、不是系统受限」的决定性证据 ——
若真到了系统容量边界，放大工作量只会让吞吐**停滞**且 P95 急剧抬升。

**依据 3（延迟余量）**：所有 sampler 的 P95 距门槛还有 3.4× ~ 25× 的余量，
且 P95 与 P50 的比值全部 < 4（无长尾失控）。

> 顺带得到一个**可外推的容量下界**：在 100 并发下，只读接口实测吞吐已到 281 req/s
> 且延迟仍处低位，说明本机 HTTP 层容量远高于 500 req/s（受限于计划模型而未能测满）。

### 3.3 真正的瓶颈在判题机，不在 HTTP 层

压测期间通过 `judge_queue_backlog` 观察到（这是在 HTTP 数字里**完全看不到**的事实）：

| 时刻 | 积压 | 说明 |
|---|---:|---|
| 压测中 | 131 → 158 → **170** | 200 次提交在 ~1 分钟内涌入 |
| 压测后 0s | 150 | |
| 压测后 10s | 142 | |
| 压测后 30s | 111 | |
| 压测后 50s | **88** | |

**单实例 `judge-worker` 的判题吞吐约 0.95 题/秒**（起容器 + 编译 + 多用例运行），
而 `POST /submissions` 可以轻松接受数十倍于此的到达速率 ——
**提交接口是异步的，它不背判题的锅，积压全部由队列吸收**。

三条结论：

1. **平台扩容的第一优先级是判题机实例数，不是 Web 服务副本数。**
   `judge-worker` 已支持多实例（9085/9185/9285），水平扩展即是线性扩容。
2. `JudgeQueueBacklogHigh > 200` 这条告警阈值**定得贴近真实**：20 线程 × 10 轮提交
   就能把积压推到约 170。这类积压**在 HTTP 指标上完全不可见**（用户看到的是「排队中」），
   正是这条告警存在的意义。
3. 积压能稳定回落，说明消费链路无泄漏；配合 `queueReconcileScan` 对账，
   不会出现 P6 修复前那种「只增不减」的虚增。

> 🔴 **本节的 1.5 题/秒 不可用于容量规划，以 §3.7 的实测标定为准。**
> 该数字是**用积压排空速率倒推**的，而排空速率被「判题首次投递缺失」缺陷与
> `pending-rescue` 的 10s 扫描周期限流 —— 量到的是**故障路径下的补偿节奏**，不是 worker 能力。
> 实测标定为 **0.95 题/秒**（口径：§3.7「排空窗口内的吞吐」），且**判题吞吐不随实例数增长**
> （3 实例实测 0.96 题/s）。

### 3.4 正确的吞吐度量方式

500 req/s 这类**恒定吞吐目标**需要**恒定负载模型**，而当前 `load.jmx` 是**固定工作量模型**。
二者不可互换。要测真实容量上限，需要下列任一种：

1. 给 `load.jmx` 增加一个**基于时长的线程组**（`ThreadGroup.scheduler=true` + `duration`，
   或 Constant Throughput Timer），让负载持续跑满 3–5 分钟再统计；
2. 使用 `-J tgXxx.loops=<大值>` 把工作量放大到远超 ramp，使观测值收敛到真实容量上限；
3. 用开环压测工具（wrk / k6 / Gatling）直接施加恒定 RPS。

**在补齐上述任一项之前，`run-perf.py` 的 500 req/s 门槛对 `load` 计划同样不成立**，
应视为「待重新标定」而非「系统不达标」。本节如实记录未达标，
按 `perf-test/README.md` §4 的约定：**不在没有依据的情况下调低门槛**。

#### 3.5.4 ⚠️ 轮次 B 首次跑出过一份**作废数据** —— 成因与规避

轮次 B 的第一次执行跑出 **1 259.6 req/s**（仅为 A 的 40%，所有 sampler 延迟均匀劣化 2.2–2.6×，
错误率仍 0）。**取证后确认是测试条件被污染，不是性能回归**，故整轮作废重跑：

| 轮次 | 精确窗口（取自 `.jtl` 首尾时间戳） | 窗口内队列积压 | 宿主 CPU 均值 / 峰值 | 吞吐 |
|---|---|---|---:|---:|---:|
| A（干净） | 09-21 18:03–18:06 | **0** | 60.6% / 74.4% | 3 108.8 |
| B⁰（**作废**） | 09-22 15:42–15:45 | **166 → 0** | **90.4% / 99.7%** | 1 259.6 |
| B（干净复测） | 09-22 15:48–15:51 | **0（全程）** | 53.2% / 67.1% | 3 266.5 |

**成因**：`run-perf.py` 的 `smoke` / `load` 计划会**真实提交**判题（10 + 200 = 210 题），
而判题要起 docker 沙箱容器 + 编译 + 逐用例运行。若紧接着启动 `throughput`，
**整轮 3 分钟窗口都与判题机抢同一份 CPU**（166 次沙箱启停），宿主 CPU 被打到 99.7%。

**三条取证手段（都是现成资产，不要靠猜）**：

```bash
# ① 精确时窗：直接读 .jtl 首尾时间戳，别信进程墙钟
head -2 perf-test/results/throughput.jtl | tail -1 | cut -d, -f1    # epoch ms
tail -1  perf-test/results/throughput.jtl | cut -d, -f1
# ② 同时段队列曲线（Prometheus 每 15s 抓一次，有历史可回溯）
curl -s "http://localhost:9090/api/v1/query_range?query=judge_queue_backlog&start=<s>&end=<e>&step=60"
# ③ 同时段宿主 CPU 饱和度（micrometer system_cpu_usage = JVM 眼里的整机 CPU）
curl -s "http://localhost:9090/api/v1/query_range?query=system_cpu_usage%7Bapplication%3D%22judge-gateway%22%7D&start=<s>&end=<e>&step=15"
```

**规避**：跑 `throughput` 前确认 `judge_queue_backlog == 0`**且整个窗口保持 0**；
`load` 结束后等 2–3 分钟。**作废的 `.jtl` 不要直接覆盖**，先归档：

```bash
cp perf-test/results/throughput.jtl \
   perf-test/results/archive/throughput-<日期>-<时刻>-contaminated-by-judging.jtl
```

> `run-perf.py` 目前**没有**排空门禁，已列入待办（`--wait-drain`）。

#### 3.5.5 关键推论

60 线程跑出 3 108.8（A）/ 3 266.5（B）req/s ⇒ 单线程约 52–54 req/s（平均响应 19ms 量级）。
Web 层（网关 + 只读接口）**离饱和还很远**，与 §3.3 的结论一致：
**真正的上限在判题链路，不在 HTTP 层。** 扩容优先级 = 判题机实例数 > Web 副本数。

> ⚠️ **单实例判题的真实处理能力**：§3.3 依据积压排空速率给出的「≈1.5 题/秒」是**在首次投递
> 缺失的缺陷路径下**测得的（排空速率被 10s 补偿扫描周期限流），**不是 worker 的真实处理能力** ——
> 实测曾出现 2 秒内出 8 个终态（≈4 题/s）。该缺陷的定位与修复见 `docs/P3-REPORT.md`；
> §3.7 已用 1 vs 3 worker 对比轮次标定：单实例 **0.95 题/秒**（口径为「排空窗口内吞吐」），
> 且**吞吐不随实例数增长**。

> ⚠️ 这仍是**同机**数字（压测工具与服务争抢 CPU、走 loopback 无网络成本），
> 只能作**容量下界**。生产容量标定必须在独立压测机做，流程见 `perf-test/RUNBOOK.md`。

> ⚠️ 本轮实测踩到一个**会让整轮数据作废**的坑并已修复：`ThreadGroup.scheduler` 曾写成
> `${__P(...)}`，而 JMeter 的 `<boolProp>` **不做函数替换**，整串被判成 `false` ——
> 「无限循环 + 调度器关闭」= 永不停止。该计划配 180s 实际跑了 13 分钟、226 万样本、
> `.jtl` 涨到 400MB 才被手工 kill。现已改为字面量 `true`，并给 `run-perf.py` 加了
> 墙钟看门狗（超时整树杀）。详见 `perf-test/README.md` §7 陷阱表与 §3.5。

### 3.7 判题吞吐重标与「多实例扩容」结论（2026-09-22 实测，**推翻了旧结论**）

> 标定工具：`scripts/measure-judge-throughput.py`（本轮新增）
> 复跑：`python scripts/measure-judge-throughput.py --n 150 --label <label>`
> ⚠️ 前置：提交限流（默认 30 次/分钟/账号）必须先放宽，脚本会打印完整流程；
> **测完必须恢复并验证**（本轮已恢复：31 次连续提交 → 前 30 成功、第 31 次 400「提交过于频繁」）。

#### 1. 测量口径（三项分开，不要混）

| 指标 | 定义 | 1 实例实测 |
|---|---|---|
| `accept_rate` | N ÷（最后一条受理 − 第一条受理） | **104 提交/s**（150 条 1.44s） |
| `drain_window` | 全部终态 − 最后一条受理 | **159.12s** |
| `throughput` | **N ÷ drain_window**（本题关注项） | **0.94 题/s** |
| `e2e P50 / P95` | 单条「受理→终态」（含排队） | **78.5s / 150.7s** |

> 采样口径（易错点）：若**等队列排空后**才逐条查终态，每条时延都会被算成
> 「整批等待时间」，P50/P95 全挤在末尾（曾量到 151.04s / 152.02s，数字整齐得像真的，其实是采样偏差）。
> 正确做法是**在排空过程中同步采样**，上表即该口径下的真实分布。

#### 2. 三组对照（同一台机、同一批 150 条 AC 提交、每次提交代码带唯一 nonce 规避幂等）

| 轮次 | 实例数 | 每实例消费并发 | 排空窗口 | 判题吞吐 | 正确性（抽样 25 条） |
|---|---:|---:|---:|---:|---|
| `1-worker` | 1 | 20（RocketMQ 默认） | 159.12s | **0.94 题/s** | **25/25 AC** ✔ |
| `3-worker`（未限并发） | 3 | 20 × 3 = 60 | 96.15s | 1.55 题/s | 🔴 **7 AC / 18 TLE** ← **正确解被判 TLE** |
| `3-worker-cap4` | 3 | 4 × 3 = 12 | 157.02s | **0.96 题/s** | **25/25 AC** ✔ |

> 第一次 `1-worker` 复跑为 1.00 题/s（150 条 / 149.49s），第二轮 0.94 —— 取 **≈0.95 题/s**。

#### 3. 两条被推翻的结论

**① 「水平扩展即是线性扩容」—— 不成立（在本机拓扑下）。**
3 实例的吞吐（0.96 题/s）与 1 实例（0.94 题/s）**基本没有差别**。
瓶颈不是 worker 线程数，而是**每个判题任务的容器启停开销**：`JudgeEngine` 对
每个用例单独走一次 `docker run`（1 个编译容器 + N 个用例容器，本批题目为 **5 个容器/题**），
而沙箱内的实际执行时间只有 **~100ms**（日志 `time=108ms`）。
反过来说，**扩容判题机的正确方向是「减少每题的容器数」**（例如全部用例合到一个容器内跑、
或引入预热容器池），而不是加实例。

**② 未限并发的多实例会「用正确性换吞吐」，而且换不到吞吐。**
3 实例 × 20 消费线程 = **60 个并发 `docker run`**，此时**容器冷启动本身**就超过了沙箱墙钟预算：

```
wallClockMs = 题目时限(1000ms) + CJ_SANDBOX_WALL_GRACE_MS(5000) = 6000ms
```

实测日志：`沙箱墙钟超时强杀：wallClockMs=6000`（**48 次**），对应
`verdict=TLE time=6000ms`。注意 TLE 的**精确判定本来是容器内 `timeout` 做的**
（Verdict 判据不变），worker 侧墙钟只是**兜底强杀** —— 但兜底把「容器还没起来」
误判成了「用户代码超时」，于是 A+B 正解被刷成 TLE。

判别实验（决定性）：同一 3 实例拓扑下**空队列逐条串行提交 5 条 → 全部 AC（28ms）**。
即假 TLE **只在并发争抢时出现**，不是系统性缺陷。

#### 4. 已落地的修复与运维约束

| 项 | 内容 |
|---|---|
| 新增旋钮 | `rocketmq.consume-thread-min/max`（`RocketMQProperties` + `RocketMQConsumerContainer`），环境变量 **`CJ_MQ_CONSUME_THREADS`**；**默认 0 = 不设置 = 行为与改动前完全一致** |
| 为什么 min/max 都要设 | RocketMQ 线程池在 `[min,max]` 间自适应；只压 max 而 min 仍是默认 20 时，池子最小仍有 20 个并发沙箱 |
| 经验公式 | **实例数 × `CJ_MQ_CONSUME_THREADS` ≤ 宿主机 CPU 核数**（本机 16 核，3×4=12 落地） |
| 验证 | 3 实例 + `CJ_MQ_CONSUME_THREADS=4` → 日志 `消费线程数已限定：min=4 max=4` → 抽样 25/25 AC |

#### 5. 容器启停是本机硬上限（微基准）

`docker run --rm --network none judge-python312 /bin/true` × N：

| 并发 | 墙钟 | 吞吐 | 单容器均值 |
|---:|---:|---:|---:|
| 1（串行 ×20） | 8.76s | 2.28 容器/s | 438ms |
| 20 | 1.82s | **11.00 容器/s** | 1605ms |
| 40 | 3.91s | 10.24 容器/s | 3492ms |

即宿主的容器启停能力约 **10–11 容器/s**（并发 20 附近饱和），按 5 容器/题折算理论上限约
**2 题/s**；而真实判题吞吐在 ~0.95 题/s 就已经打平 —— 差额来自每题的多余开销
（`docker image inspect` 预检、两处 `-v` 挂载、`--tmpfs`/seccomp/`--cpus` 等重参数、
DB/Redis/Feign 往返、工件读写）。**继续加并发只会把差额换成假 TLE，不会变成吞吐。**

> ⚠️ 以上均为**同机**数字（判题、Docker、压测工具同机）。生产标定仍需按
> `perf-test/RUNBOOK.md` 在独立环境做，且**多实例必须落在不同宿主机**才可能接近线性。

### 3.8 长稳首跑（`--plan soak` 10 分钟）—— 容器化栈（2026-10-01）

首轮 soak 在**容器化全栈**上跑（compose 8 服务 + 网关 9080），结论：**链路长稳无劣化**。

| 指标 | 实测 |
|---|---|
| 样本 / 错误 | **1,270,883 / 0（0.000%）** |
| 有效窗口 | 599.8s（按样本时间戳跨度） |
| 整体吞吐 | 2118.7 req/s（soak 低并发长稳，容量标定用 `--plan throughput`，见 §3.5） |
| P95（四采样器） | problems/page **15ms**、problems/{id} **13ms**、submissions/page **10ms**、contests/{id}/rank **11ms**（门槛 300/300/400/300ms，余量 20–40×） |
| 观测项（RUNBOOK §3.2） | jvm heap 锯齿回水位正常；`hikaricp_connections_pending` 窗口内恒 0（6 服务）；`judge_queue_backlog` 恒 0；跑完 `verify-p1-login` **43/0** 无静默损坏 |

**login P95=804ms FAIL 是小样本伪告警（解读，勿照抄进告警）**：soak 里 login 挂在
OnceOnlyController（每线程一次，n=18）。18 样本实值：15 个 97–136ms + 1 个 181ms +
**2 个 804ms**（ramp 起步的两个预热离群点：首次连接建立 + auth 侧冷启动），全部 HTTP 200。
n=18 时 P95 插值正好落在两个离群点上 —— **500ms 门槛对 soak 的 login 无统计意义**，
login 延迟门槛只在 load/throughput 计划（大样本）下判。稳态 login 延迟 P50≈123ms，健康。

**限流注意**：本轮按 soak.jmx 头部说明放宽 `GW_LOGIN_RATE_REPLENISH=500/BURST=1000` 跑测，
测后恢复 2/5 并实测 429 仍生效（12 连发 → {200:6, 429:6}）。事后结论：soak（18 线程）
登录速率 ≈0.6/s < 2/s replenish，**其实不必放宽**；该说明是给 load（100 线程）的。

#### 3.8.1 1h 全量首跑 —— 被 30 分钟 token 过期截断（2026-10-01，如实记录）

1h soak（`--plan soak --no-html`）实际跑了 **55:40**（19:09:19 启动），**未跑满 1h 亦未产出
PASS/FAIL 结论**——后台任务进程树随上一会话结束被连带回收（非看门狗 63min、非 JMeter 自身调度）。
数据本身完整落盘（soak.jtl 2.9GB / 1488 万行），按时间轴分两个阶段，结论完全不同：

| 阶段 | 窗口 | 样本 | 错误 | 吞吐 | 说明 |
|---|---|---:|---:|---:|---|
| ① 干净负载 | 19:09:19 → 19:39:00（29:40） | **4,465,338** | **0（0.000%）** | ≈2511/s | avg 7–8ms，与 10min soak 结论一致 |
| ② 401 风暴 | 19:39:30 → 20:05（被杀） | ≈1041 万 | **~81.7%/区间** | 6400–6900/s | avg 2ms，全部 **401 Unauthorized** |

**阶段②的根因是负载模型限制，不是系统缺陷**：`ACCESS_TOKEN_TTL = 30min`
（`AccountService.java` 常量），soak 计划每线程只登录一次（OnceOnlyController）且不续签，
**恰好在第 30:10 分全部 token 同时过期**。旁证链完整：

- 失败的全部是**带鉴权**接口（`/submissions/page`、`/contests/{id}/rank`、`/problems/{id}`），错误码统一 401；
- `GET /problems/page`（T6 public-read 路径，匿名可访问）在风暴期**全程 100% 成功**——
  同一窗口抽样 20 万行：page 全 OK，三个鉴权接口全 401，边界与 T6 设计严丝合缝；
- 错误率从 0% → 14.26% → 76-82% 的爬坡正好是 18 个线程 token 相继到期的过渡带。

**两条意外收获（可入正册的韧性数据点）**：

1. **网关拒绝路径抗压**：401 风暴期网关以 6900 req/s 吞吐、avg 2ms 持续拒绝过期 token，
   无 5xx、无连接堆积、无崩溃——网关的认证失败路径比正常代理路径更快且同样稳定。
2. **public-read 边界实测验证**：30 分钟风暴窗口里匿名接口持续 200，鉴权接口持续 401，
   是 T6 METHOD-AWARE public-read 设计的**大规模实测背书**。

**有效 1h soak 的达成条件（T4 遗留，见 HANDOFF）**：三选一——
a) soak.jmx 增加定时重登（token 到期前刷一次）；
b) 压测专用账号 TTL 放长（仅 perf profile）；
c) 每线程定时走 refresh 换发。
在补齐任一项之前，**长稳有效窗口以 10min soak（§3.8 全绿）+ 1h 首跑前 30 分钟（446 万样本 0 错误）为准**。

## 四、告警阈值与实测的对应关系


`deploy/monitoring/prometheus/rules/codejudge-alerts.yml` 的 11 条阈值取自本报告：

| 告警 | 当前阈值 | 与实测的关系 |
|---|---|---|
| `CodeJudgeHighLatencyP95` | 业务 P95 > **0.3s** | 恒定负载下最慢 P95 = 82ms（`/problems/{id}`）、登录 139ms → **余量 2.2×（相对登录）**。已修正口径：排除 `/actuator` 与 SSE |
| `HikariPoolSaturation` | 平均获取连接耗时 > **0.2s** `or` acquire 超时 > 0 | 健康态实测 7.6ms（judge-problem）→ 余量 26×。**判据已换**：原 `pending > 5` 被证伪（见下） |
| `JvmHeapHigh` | 堆 > 85% 持续 10m | 未触发 |
| `JudgeQueueBacklogHigh` | 积压 > 200 | `load` 计划下 200 次提交使积压峰值 **170**（单 worker ≈0.95 题/s，见 §3.7）→ 阈值贴近真实，可用 |
| `CodeJudgeHighErrorRate` | 5xx > 1% | 实测 **0.000%**（559 035 样本） |
| `CodeJudgeSubmitFailureBurst` | 提交 5xx > 0.5/s | 过滤条件已收紧为 `method="POST", uri="/submissions"`（原 `uri=~"/submissions.*"` 会混入只读列表页） |

#### ⚠️ `HikariPoolSaturation` 阈值不可用（本轮实测）

判据 `hikaricp_connections_pending > 5` 在**健康状态**下就会触发：

| 观测 | 值 | 说明 |
|---|---|---|
| 持续负载 | ≈2 900 req/s（13 分钟） | 失控压测那轮（见 §3.5 注） |
| `hikaricp_connections_pending` 峰值 | **29** | 远大于 5 → 告警真的触发了（`for: 3m`） |
| 同期 P95 / 错误率 | 82ms / **0.000%** | 用户侧完全健康 |
| 同期 `acquire_timeout_total` | **0** | 没有任何请求拿不到连接 |
| 平均获取连接耗时 | 7.6ms | 排队存在，但每次只等 7.6ms |
| 负载停止后 | active 10→0、pending 29→0（数秒内） | **不是泄漏**，池子调度正常 |

结论：`pending` 衡量的是"有没有线程在排队"，而排队是 10 个连接服务 60 个并发线程时的**正常复用行为**。继续用它等于给健康系统报 warning，把真正的故障淹掉。

新判据改用**平均获取连接耗时**（`rate(acquire_seconds_sum) / rate(acquire_seconds_count)`），它直接对应"用户等了多久"；再 `or` 上 acquire 超时次数兜住"已经有人失败"。

> ⚠️ **这些阈值仍只适用于本地基线，上线前必须按真实容量重标**（独立压测机流程见 `perf-test/RUNBOOK.md`）。
> 连接池阈值 0.2s 相对实测 7.6ms 有 26× 余量，仍属"偏钝"，需在生产流量下收紧。
> 重标工具 `scripts/recalibrate-alerts.py` 已有两道守卫：样本稀疏的 URI 不计入延迟基线、
> 无提交流量时不改提交阈值 —— 没有数据就不改，好过凭残缺数据调。
